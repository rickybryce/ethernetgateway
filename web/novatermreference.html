What this page is

NovaTerm 9.6c by Nick Rossi is the terminal this gateway is tested against for Commodore file transfers — it is the real peer for Punter, and it speaks the XMODEM and Kermit families too. Everything below was measured against NovaTerm 9.6c running on an emulated C64 (VICE 3.7.1) wired to the gateway, not taken from a manual. Where a fact cost a wrong turn to learn, the wrong turn is recorded with it, because the wrong turn is the useful part.

Two of these bite while you are experimenting. C= H hangs up, and C= C is the 40/80 column toggle, not a screen clear — in 80-column mode the screen moves and a 40-column reader returns nonsense. Finding the command list by trial cost two dropped calls before reading it off the C= M screen.

The protocol resets to Zmodem. That is the BASIC loader's default (pt$="Zmodem"), and NovaTerm loads prt.Punter from disk only when Punter is selected. A Punter test run against a Zmodem receiver fails in a way that looks exactly like a protocol defect. Set it explicitly with C= P every run, and confirm it on the status line.

Running a transfer

  1. Set the protocol with C= P; wait for the module to load from disk.
  2. Dial, and answer the gateway’s terminal detection with INST/DEL so it detects PETSCII.
  3. On the gateway: F File Transfer, then D Download or U Upload, pick the file, pick the protocol.
  4. On the C64: C= D to receive or C= U to send, then give a filename.
  5. The gateway allows 45 seconds to start.
Getting the file back off the disk. NovaTerm leaves a completed download as a splat (unclosed) directory entry: c1541 -read refuses it, and c1541 -validate deletes it. Copy the .d64 first, then walk the sector chain directly — the data blocks are all there.

Driving it under VICE

tools/punter-vice-harness/ drives NovaTerm with no human in the loop. Two channels are needed, and each has a trap.

Read the screen VICE remote monitor, following $D018 and CIA2 $DD00 Assuming $0400. NovaTerm relocates its screen to $8C00; reading the default returns stale memory that looks like a decoder bug.
Type at it X11 XTEST into the VICE window (window must be mapped, need not be focused) VICE’s own keybuf monitor command. It stuffs the KERNAL buffer; NovaTerm scans the CIA1 matrix itself and never looks.

The menu remembers where it was left; counting walked into “Exit terminal / Are you sure?”. Testing bit 7 alone does not work either: every row of the menu box is reversed.
Hang up +++, guard time, ATH, then prove it with AT → OK Relying on NovaTerm’s C= H over a socat PTY: it drops DTR, and a PTY carries no modem control lines. Also waiting for “no carrier”, which only appears if a call was up.
Load quickly -warp for the disk load, then Alt+W once to turn it off Leaving warp on for the transfer. At 241% the ACIA drops bytes — NovaTerm’s modem init arrives with every letter missing. Blind-toggling turns it back on for a second run.

NovaTerm takes about a minute to start because the BASIC loader pulls nova9.6-1.ml, nova9.6-2.ml, the RTL and the terminal module off an emulated 1541 in sequence, at authentic drive speed. That is not a stall.

Measured results

Payload: PUNTEST.SEQ, 1775 bytes — every byte value four times over, long runs of CAN, XON, XOFF, SUB, CR, LF, FF, DEL and BS, and a tail spanning a 255-byte block boundary.

All twenty-four paths — six protocols, both directions, both links — compared byte for byte against that payload. A download is read back out of the C64's own disk image and is identified by the unclosed directory entry rather than by name, because the transfer disk is seeded with a file of the same name before every run and a name match grades the seed. YMODEM's upload arrives with three bytes of trailing SUB, and the XMODEM family's with padding to the next 128-byte boundary: neither protocol carries an exact length from this sender — NovaTerm's YMODEM block 0 states a block-count estimate (7 × 254 = 1778) rather than the true 1775 — so the padding is correct behaviour and is reported with its byte count rather than trimmed away.

The telnet path found a real defect. Before v1.0.0-RC1 the gateway refused RFC 856 BINARY, while already treating transfers as 8-bit (no NVT CR-NUL stuffing, by explicit decision in tnio). It therefore told a telnet peer the opposite of what it did, and an NVT-conformant peer applied text rules to the blocks: the same payload that arrived byte-perfect over serial never got past block 0 through tcpser — 32 rejections. Agreeing to BINARY, in both directions, took it to zero. The serial path was the control that made this a diagnosis rather than a guess.
Two notes on the upload direction. NovaTerm reports the file’s allocated size — 7 blocks, 1778 bytes for a 1775-byte file — but sends the true length, and the gateway records 1775. And the saved name is derived, not taken: a requested puntup.seq is stored as puntupseq.usr, because CBM names carry no dot and the extension comes from the Punter type byte, which NovaTerm declares as USR for a SEQ file.
