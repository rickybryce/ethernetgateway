Overview

Gopher is the internet's menu system: a 1991 protocol from the University of Minnesota that predates the web's rise and still has hundreds of servers run by hobbyists. This page explains how it works on the wire and exactly how the gateway's browser speaks it.

Where the web is pages with links inside the text, Gopher is menus. Every screen is a list of items, and each item is one thing: another menu, a text file, a search, a file to download, or a telnet session. There is no layout, no styling, no scripts and no images on the page. That makes it one of the few corners of the internet that a 40-column Commodore 64 or an 80-column terminal can use completely.

The protocol is deliberately tiny. The client opens a TCP connection (port 70 by default), sends one line naming what it wants, and reads until the server closes. There are no headers, no cookies and no state between requests. Gopher+ (1993) adds, in an upward-compatible way, information about each item, alternate formats, and simple forms.

What the gateway implements: every item type in RFC 1436, the gopher:// URL scheme of RFC 4266, and Gopher+ — item information, views and +ASK forms. The compliance table lists each requirement and where it stands.

A good first stop: gopher://gopher.floodgap.com. Its menu includes a search of all of Gopher, and it links to most of the other servers still running.
One Transaction

Every request is a new connection, one line out, one reply back.

C: connects to host, port 70
C: selector CR LF
S: the menu, text file or binary file
S: closes the connection

The selector is an opaque string the server handed out in an earlier menu; the empty selector asks for the server's top menu. The client never interprets a selector: it sends back exactly what it was given. A menu or text file ends with a line holding a single . (the Lastline), and a binary file ends when the server closes.

RFC 1436 says either side may close once the reply is complete. The gateway reads until the server closes, but when a text file or menu has ended with its . line (a dot, then CR LF, as the RFC writes it) it waits only two more seconds, so a server that keeps the connection open costs a moment rather than a timeout.

Menus

A menu is one item per line, its fields separated by TABs.

TDisplay string<TAB>selector<TAB>host<TAB>port[<TAB>+] CR LF
FieldMeaning
TypeOne character: what the item is (table below). It is glued to the display string.
Display stringWhat the user sees. Should be under 70 characters, in ISO Latin-1 if it uses 8-bit characters.
SelectorWhat to send to fetch it. Any bytes except TAB, CR and LF.
Host, portWhere it lives — any server, not just this one. An empty host or port means this server.
Fifth fieldGopher+ only: + marks a Gopher+ item, ? one with a form. Old clients ignore it.

The gateway numbers each followable item as a link and labels it by what following it will do. Lines of type i (information, a widespread extension) are shown as plain text, and type 3 (an error) is shown prefixed ERR:.

Text Files & the Dot Line

Why a server doubles some dots, and why a line can come out one dot short.

Gopher never says how long a text file is. The server ends it with a line holding a single ., the way mail servers end a message they pass on. That would cut the file short wherever a line of the file itself starts with a dot, so RFC 1436 has the server add an extra dot to every such line, and the client take it off again: 

The file:          On the wire:       Shown:
Hello              Hello              Hello
.hidden            ..hidden           .hidden
...                ....               ...
                   .                  (end)

The gateway does the client's part for text files and the two text encodings of a file (types 0, 4 and 6): it hides the closing line and takes one dot off any line that starts with two.

Servers that skip their part: many servers in use today (Bucktooth on Floodgap, gophernicus, pygopherd, all measured) send files as they are, without doubling. From those, a line that really begins with two or more dots is shown with one fewer. The gateway follows the standard, for the servers that follow it too.

Text that is not valid UTF-8 is read as ISO Latin-1, the character set both specifications name, one line at a time; a Latin-1 é is drawn as itself. On a C64 or a 7-bit terminal it is folded the way all internet text is.

Searches & Phone Books

Two item types ask the user something first.

Type 7: full-text search
C: selector<TAB>words CR LF
S: a menu of what matched

The browser asks Search:, sends the words after a TAB, and draws the reply as a menu. Spaces mean and; some engines also take and, or and not. The words stay in the page's URL, so Back, Reload and bookmarks repeat the search.

Type 2: CSO phone book
C: query name CR LF
C: quit CR LF
S: -200:1:name: Ricky Bryce
S: -200:1:email: ...
S: 200:Ok.

A CSO item is not Gopher at all: RFC 1436 says the client must “resort to a pure CSO nameserver protocol”. The browser asks Look up:, connects to the item's host (port 105 if the menu gives none), and shows each matching entry's fields. Codes of 500 and up are errors. Lookups only: logging in and changing entries are left out.

Redundant Servers

A + item is the item above it, held on another server.

1Documents<TAB>/docs<TAB>main.example<TAB>70
+Documents<TAB>/docs<TAB>mirror.example<TAB>70

The item a + stands in for is the last one above it that is not a +, and it is fetched as that item's type. Both are listed, the copy marked [ALT], so either can be picked.

RFC 1436 §3.5 also asks a smart client to move to the copy when a server “seems to be down”. The gateway does: following any of them, it tries the others in menu order, at most three, when the server cannot be reached — its name does not resolve, or nothing answers. A server that answers, even with an error or a missing item, is up, and its answer stands. This covers menus, text, searches (the copy is asked the same words), phone books and downloads. No more than three copies are tried, because each one that is down can take 15 seconds to give up on.

Telnet & tn3270 Items

Types 8 and T are sessions, not documents.

RFC 1436: “Connect to given host at given port. The name to login as at this host is in the selector string.” The browser shows the host and the name to log in as, asks, and hands you to the gateway's own Telnet Gateway. Pressing ESC twice leaves and returns to the menu. Port 23 is used when the menu gives none.

Every address the host name resolves to is checked against the same rule as any other fetch (see safety), and the address checked is the one dialled — the name is not looked up a second time.

tn3270: a T item is a session with an IBM mainframe, which expects a 3270 block-mode terminal. It is connected over plain telnet, and the screen says so before connecting; many 3270 hosts do not work that way.
URLs & Selector Bytes

RFC 4266 is how a gopher item is written as an address.

gopher://host[:port]/Tselector[%09search[%09gopher+ string]]
PartRule
Port70 when omitted.
TThe item type. With no path at all, 1 (a menu) and the empty selector.
SelectorPercent-encoded. gopher://host/0/my%20file asks for my file.
%09 searchA search's words, after an encoded TAB.
%09 Gopher+ stringAfter a second TAB (the search may be empty): +, !, $, a view or ?.

A selector is bytes, not text. Both RFCs allow any byte but TAB, CR and LF. The gateway keeps a selector as the exact bytes the menu gave: a Latin-1 é is written %E9 in the URL and sent as that one byte, so a server whose selectors are not UTF-8 is asked for what it listed. A gopher address typed at G, and the words typed at a search prompt, go the same way: as the bytes the terminal sent. Bookmarks, Back and Reload keep the whole URL, search and Gopher+ string included.

Gopher+

Upward-compatible extensions: item information, alternate formats and forms.

A Gopher+ server marks its items with the menu's fifth field, and a Gopher+ request adds a TAB and a command after the selector. The gateway sends Gopher+ requests only for items marked + or ?, because servers that do not speak it vary: Floodgap and SDF ignore the extra field and send the plain reply, and the gateway takes a reply with no Gopher+ header as the plain reply it is.

RequestAsks for
selector<TAB>+The item, in its default view.
selector<TAB>+text/plain En_USOne of its views (formats), by MIME type and language.
selector<TAB>!The item's attributes.
selector<TAB>$The attributes of every item in a menu.
selector<TAB>words<TAB>+A Gopher+ search.
Replies
First lineMeans
+5340Exactly 5340 bytes follow.
+-1Data ends with a . line (dots doubled, as in text files).
+-2Data ends when the server closes.
--1 …An error. Its first token is a code: 1 not available, 2 try again later, 3 moved — followed by the menu line of where it went, which the gateway shows as a link.

A counted reply ends the read as soon as its bytes are in, without waiting for the server to close. A download that arrives short of what its header promised is refused rather than saved as if whole.

Only a Gopher+ form can send a file. A form counts as one only when it came from an +ASK block, on a gopher page, and is sent to a gopher item — so no web page can make the browser send a file from the transfer folder. The Gopher+ spec suggests limiting ChooseF to one directory; the gateway offers only the transfer folder's own files.
Safety & Limits

A menu can point anywhere, so what it points at is checked.

RuleWhy
Hosts on this machine or the local network are refused, unless disable_ip_safety is on.A menu on the internet must not be able to reach your LAN through the gateway. Every address a name resolves to is checked, and the checked address is the one connected to.
Control characters are stripped from everything shown, the C1 range included.A hostile server could otherwise move the cursor or rewrite the screen.
Pages: 512 KB, 15 seconds for the whole exchange with each server. At most three + copies are tried after a server that is down.A server trickling bytes, or a menu listing many dead copies, cannot hold the session.
Files: 8 MB, 180 seconds.What the transfer protocols can send on; time for a slow server.
After a . line: 2 seconds more at most.Either side may close then.

Glossary
TermMeaning
SelectorThe string a client sends to fetch an item. Opaque to the client; any bytes but TAB, CR and LF.
