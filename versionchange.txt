# ── FILES THAT ARE NOT VERSION STRINGS ──────────────────────────
#
# This list answers "what must be BUMPED".  Two kinds of release mistake it
# cannot catch, both of which have happened:
#
#   1. A file that should have been ADDED.  v0.9.0 shipped `EGT80.COM` in the
#      release tarball and not `EGT8080.COM`, which had existed since
#      2026-08-07 and is the terminal the manual tells you to reach for.
#      Nothing was broken -- both are compiled into the binary -- but the loose
#      copy exists so you can XMODEM it to real hardware without starting the
#      emulator, and the recommended one was missing.  The packaging step in
#      `.github/workflows/release.yml` has TWO branches (Unix `cp`, Windows
#      `Copy-Item`); a file added to one and not the other is worse than one
#      added to neither, because it ships on some platforms only.
#
#      The Z80 build was retired during 0.9.2's cycle and brought back
#      before that release was cut, because the Z180 ASCI ports -- an
#      SC126's console -- are reached with ED-prefixed instructions that
#      cannot exist in an 8080 binary.  So the pair is live again and BOTH
#      .COM files must ship, from both branches of that step.
#
#      When you add something users are meant to receive, add it there and
#      say so here.  Currently shipped alongside the binary:
#        README.md  LICENSE  EGT8080/EGT8080.COM  EGT8080/EGT80.COM
#
#   2. A generated file edited by hand.  THIRD-PARTY-NOTICES.md is produced
#      wholesale from `about.toml` + `about.hbs` and says so at the top.  Our
#      own prose in it -- the z80pack and derived-work notices -- lives in
#      `about.hbs`.  Edit the .md alone and the next regeneration silently
#      drops it, which is a licence-notice loss, not a cosmetic one.  Edit
#      `about.hbs`, then regenerate.  `about.hbs` carries no version string of
#      its own (cargo-about injects it from Cargo.toml), which is why it is
#      not in the bump list above.
#
#   3. A generated file that has gone STALE.  `src/cpm/repodisks.txt` is the
#      catalogue of what is on every disk in the collections this gateway
#      runs -- compiled in with include_str! and written into CPM/images beside
#      the readme.  It is produced by the #[ignore] `record_repodisks` test,
#      which mounts every image through the product's own path and reads its
#      real directory:
#
#        REPODISKS_RECORD=1 cargo test --release --bin ethernetgateway \
#          -- --ignored --nocapture record_repodisks
#
#      **THE ENV VAR IS NOT OPTIONAL AND ITS ABSENCE IS SILENT.**  This
#      line lacked it until 2026-09-19, and without it the test prints
#      "REPODISKS_RECORD=1 not set; skipping" and passes in 0.00s --
#      so a release check that runs the documented command, diffs the
#      file and finds it unchanged has proved nothing at all.  That is
#      the same shape as the six interop gates that spent an unknown
#      period passing without running: demand positive evidence in the
#      output ("wrote src/cpm/repodisks.txt: N disks"), never the pass.
#      Its partner above shows `NONBOOTING_RECORD=1` correctly, which is
#      why only this one went unnoticed.
#
#      Re-run it when a disk format is added (a disk we could not read before
#      will now list its files instead of saying it has no CP/M filesystem),
#      when a collection is added to the REPOS table, or when those upstream
#      repos gain disks.  It carries no version string, so nothing above will
#      remind you -- and a catalogue that is quietly a year out of date is the
#      kind of wrong that still looks right.  It is also pinned to LF in
#      .gitattributes, because its shape is the product.
#
#      `src/cpm/nonbooting.txt` is its partner and goes stale the same way:
#      the disks MEASURED never to reach a sign-on, which the three boot
#      pickers withhold and which repodisks.txt explains.  Produced by the
#      #[ignore] `record_nonbooting`, which BOOTS every image rather than
#      reading a sector -- the reason it exists is that the IMSAI disks all
#      pass the sector test and then run into a controller nothing answers:
#
#        NONBOOTING_RECORD=1 cargo test --release record_nonbooting \
#          -- --ignored --nocapture
#
#      **THE ORDER MATTERS AND IT IS NOT OBVIOUS.**  nonbooting.txt is
#      compiled in with include_str!, and record_repodisks reads it through
#      image_can_boot -- so a rebuild has to sit BETWEEN the two:
#
#        1. record_nonbooting      (writes nonbooting.txt)
#        2. cargo build --release  (compiles the new table in)
#        3. record_repodisks       (writes repodisks.txt from it)
#
#      Run them the other way round and the catalogue is regenerated against
#      the PREVIOUS list, so it goes on marking a disk "boots" that the
#      pickers have already stopped offering -- the exact disagreement between
#      the catalogue and the picker that this pair was built to end, arriving
#      by way of the fix for it.  Re-run both when a controller is added
#      (disks withheld for wanting it start booting), when a collection joins
#      REPOS, or when those repos gain disks.
#

# ── BEFORE TAGGING: check CI, not just the local suite ─────────
#   gh run list --workflow=ci.yml --limit 5
#     Every recent master run must be `success`.  A local `cargo test` is NOT a
#     substitute: CI runs the suite on ubuntu, macOS AND Windows, and a
#     platform-specific failure is invisible here.  0.8.0 was tagged with the
#     Windows job red for three pushes because only the local suite and the
#     *release* workflow were checked — release.yml builds and signs, it never
#     runs the tests, so it is green regardless.
#   gh run view <id> --log-failed        # if red, before doing anything else
#
# ── release.yml IS NOT COVERED BY CI ───────────────────────────
#   Nothing runs this workflow but a tag push, so a change to it is untested
#   until a release cut -- and the thing most likely to change it is not a
#   person.  1.0.0-RC2 stopped dead in `sign & publish` because a Scorecard
#   pin bump (`sigstore/cosign-installer@v3` -> `@v4.1.2`, cut AFTER RC1) moved
#   the default cosign from 2.x to 3.0.6, where `--new-bundle-format` defaults
#   to true and ignores the `--output-signature`/`--output-certificate` flags
#   this workflow passes.  Four build jobs green, no release published.
#
#   So: after ANY dependabot or Scorecard change to release.yml, read what the
#   bumped action actually installs -- pinning the installer does not pin the
#   tool -- and if a CLI is involved, run the exact command against that
#   version before the next cut.  `gh release download -R <repo> <tag> -p <asset>`
#   gets the binary; a validation error appears immediately, well before the
#   network work, so even a sandbox with no egress gives a verdict.
#
#   RC2 was rescued with `--new-bundle-format=false --use-signing-config=false`,
#   and that was a STOPGAP, now spent: v3.1.3 deprecates `--new-bundle-format`
#   itself ("this will be the only supported format in future versions").
#   This workflow now signs into one `<name>.sigstore.json` bundle per artifact
#   with no flags but `--bundle`, which is cosign 3's own default path.
#   Verifying a bundle needs cosign v2.5+ (measured: 2.4.0 refuses it).
#
#   A failed cut with no release published is recovered by fixing the workflow
#   and re-pointing the tag (delete the remote tag, re-tag, push).  Do NOT use
#   the `workflow_dispatch` tag input for this: `NAME=` and the release name
#   both read `github.ref_name`, which under a dispatch is the BRANCH -- the
#   assets would be published as `ethernetgateway-master-<target>`.
#
# ── AFTER TAGGING: watch the release pipeline ──────────────────
#   gh run list --workflow=release.yml --limit 3
#   until [ "$(gh run view <id> --json status -q .status)" = completed ]; \
#       do sleep 30; done; gh run view <id> --json conclusion -q .conclusion
#   gh release view vX.Y.Z --json assets -q '.assets | length'   # expect 18
#     6 payloads + 6 .sha256 + 6 .sigstore.json.  It was 24 up to 1.0.0-RC2,
#     when the signature was a .sig + .pem PAIR; one bundle replaced the two.
#   Then spot-check one artifact.  Two things bite here every time:
#     * `gh release download` refuses to run inside this repo -- "Stopping at
#       filesystem boundary".  Run it from a scratch directory and pass
#       `-R rickybryce/ethernetgateway`.
#     * the .sha256 files record the path as `dist/<name>`, so `sha256sum -c`
#       must be run with the tarball inside a `dist/` subdirectory or it
#       reports "No such file" -- which reads like a corrupt download.
#   Then extract and run the binary to confirm it prints the new version, and
#   check the archive contains everything in the shipped-files list above.
#
#   VERIFY ONE SIGNATURE -- a correctly *named* .sigstore.json proves nothing:
#     cosign verify-blob --bundle <artifact>.sigstore.json \
#       --certificate-identity \
#         "https://github.com/rickybryce/ethernetgateway/.github/workflows/release.yml@refs/tags/vX.Y.Z" \
#       --certificate-oidc-issuer https://token.actions.githubusercontent.com \
#       <artifact>
#   The identity must name the TAG.  A bundle that verifies under a different
#   ref is a bundle signed by a different run, which is the thing being checked.
